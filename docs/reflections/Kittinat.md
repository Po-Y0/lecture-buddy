คำถามข้อ 1 : จากแนวคิด "Software Entropy" และ "Broken Window Theory" ลองมองย้อนกลับไปในโปรเจกต์ที่คุณเคยทำ มี "หน้าต่างที่แตก" บานไหนที่คุณเคยปล่อยปละละเลย และมันส่งผลกระทบอย่างไรในระยะยาว?

ANS : จากแนวคิด **Software Entropy** และ **Broken Window Theory** เมื่อลองมองย้อนกลับไปในโปรเจกต์ที่เคยทำ “หน้าต่างที่แตก” ที่ผมเคยปล่อยไว้คือ **การกำหนดขอบเขตของระบบกว้างเกินไป แต่ไม่ได้รีบตัดให้ชัดเจนตั้งแต่แรก** โดยในช่วงเริ่มต้นของโปรเจกต์ ระบบถูกวางไว้ให้วิเคราะห์หลายอย่างพร้อมกัน เช่น ท่าทาง สีหน้า สายตา และเสียงพูด แต่ยังไม่มีการแยกให้ชัดว่าอะไรจำเป็นจริง อะไรวัดได้จริง และอะไรควรตัดออกก่อนเพื่อให้พัฒนาได้ทัน

ในตอนแรกปัญหานี้ดูเหมือนเป็นเรื่องเล็ก เพราะคิดว่าสามารถค่อย ๆ ปรับภายหลังได้ แต่เมื่อเวลาผ่านไป มันเริ่มทำให้โปรเจกต์ซับซ้อนขึ้นเรื่อย ๆ ทีมต้องเสียเวลาคิดหลายทางพร้อมกัน ทั้งโมเดลภาพ โมเดลเสียง การตีความพฤติกรรม และการเชื่อมกับรูบริคคะแนน ทำให้การออกแบบระบบไม่คมชัด และยากต่อการนำไปเขียนโค้ดจริง

ผลกระทบระยะยาวคือเกิด **Software Entropy** ภายในโปรเจกต์ กล่าวคือ งานเริ่มมีความยุ่งเหยิงมากขึ้น แม้ยังไม่ได้เขียนโค้ดจำนวนมาก แต่ความไม่ชัดเจนของ requirement ทำให้เอกสาร การออกแบบฟีเจอร์ และ logic การคำนวณเริ่มไม่สอดคล้องกัน เช่น บางพฤติกรรมดูน่าสนใจแต่ไม่มีวิธีวัดที่แน่นอน หรือบางเกณฑ์ในรูบริคแยกคะแนนระดับ 2 กับ 3 ได้ยากมาก

สุดท้ายทีมต้องย้อนกลับมาตัดขอบเขตใหม่ โดยลดจากการวิเคราะห์หลายมิติ เหลือเน้นเฉพาะพฤติกรรมร่างกายที่ตรวจจับได้จาก keypoints เช่น การขยับมือ การหันตัว และความนิ่งของร่างกาย การแก้ไขนี้ช่วยให้โปรเจกต์กลับมาชัดขึ้น แต่ก็ทำให้เสียเวลาไปพอสมควร เพราะถ้าจัดการ “หน้าต่างที่แตก” ตั้งแต่แรก ระบบอาจออกแบบได้เป็นระเบียบและเดินหน้าได้เร็วกว่านี้

บทเรียนที่ได้คือ ในการทำซอฟต์แวร์ ปัญหาเล็ก ๆ อย่าง requirement ที่คลุมเครือ หรือ feature ที่กว้างเกินไป ไม่ควรถูกปล่อยทิ้งไว้ เพราะมันจะค่อย ๆ ทำให้ทั้งระบบซับซ้อนขึ้น และส่งผลต่อการตัดสินใจในทุกขั้นตอน การรีบแก้ “หน้าต่างที่แตก” ตั้งแต่เริ่มต้นจึงช่วยลดความยุ่งเหยิงของโปรเจกต์ในระยะยาวได้มาก

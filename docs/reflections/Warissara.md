คำถามข้อ 1 : จากแนวคิด "Software Entropy" และ "Broken Window Theory" ลองมองย้อนกลับไปในโปรเจกต์ที่คุณเคยทำ มี "หน้าต่างที่แตก" บานไหนที่คุณเคยปล่อยปละละเลย และมันส่งผลกระทบอย่างไรในระยะยาว?

คำตอบ : ในโปรเจกต์ก่อนหน้านี้ "หน้าต่างที่แตก" ของฉันคือการปล่อยให้มีโค้ดรกๆ โค้ดที่ไม่ได้ใช้แล้ว หรือพวก Logic แปลกๆ ค้างไว้ในโปรเจกต์โดยไม่ยอมเคลียร์ค่ะ คิดแค่ว่า "เดี๋ยวค่อยกลับมาแก้ตอนท้าย"

พอปล่อยทิ้งไว้เรื่อยๆ มันก็เกิด Software Entropy คือคนอื่นในทีมพอมาเห็นโค้ดส่วนนี้รก ก็เริ่มปล่อยเบลอและเขียนโค้ดลวกๆ ตามกัน เพราะรู้สึกว่าโครงสร้างเดิมมันก็ไม่ได้เป๊ะอยู่แล้ว สุดท้ายพอโปรเจกต์ใกล้เดดไลน์ โค้ดก็พันกันมั่วจนแก้ยาก เกิด Bug สะสม และทำให้ทีมพัฒนาต่อได้ช้าลงมาก

คำถามข้อ 2 : อธิบายหลักการ "Take Responsibility" ในความเข้าใจของคุณ และยกตัวอย่างสถานการณ์ที่คุณจะนำหลักการ "Provide Options, Don't Make Lame Excuses" ไปใช้ในการสื่อสารกับเพื่อนร่วมทีมในโปรเจกต์นี้

คำตอบ : "Take Responsibility" คือการกล้ารับผิดชอบงานที่ตัวเองถืออยู่แบบ 100% ถ้างานเสร็จก็คือดี แต่ถ้าเกิดปัญหาหรือทำพัง ก็ยืดอกยอมรับ ไม่โทษฟ้าโทษฝน ไม่โทษคอมช้า หรือโทษว่าเพื่อนส่งงานให้ช้า แต่โฟกัสไปที่การช่วยทีมแก้ปัญหาแทน

ตัวอย่างการใช้ "Provide Options, Don't Make Lame Excuses" ตอนส่งงานไม่ทัน :

แบบที่ห้ามทำ (แก้ตัวลอยๆ) : "ช่วงนี้งานคณะเยอะมาก แถมคอมก็อืดด้วย น่าจะทำฟีเจอร์นี้ให้เสร็จตามเวลาไม่ได้แล้วนะ" (บ่นแล้วทิ้งภาระให้เพื่อนงงต่อ)

แบบที่เป็นมืออาชีพ (เสนอทางเลือก) : "ทุกคนคะ พอดีฟีเจอร์นี้ติดปัญหาทางเทคนิคนิดหน่อย น่าจะส่งไม่ทันเย็นนี้ ต้องขอโทษด้วยจริงๆ นะ แต่ตอนนี้คิดทางออกไว้ 2 ทาง ทีมเห็นว่าแบบไหนดีกว่ากันบอกได้เลยนะ เช่น
    - ขอเลื่อนไปส่งพรุ่งนี้เที่ยง เดี๋ยวคืนนี้ฉันจะลุยเคลียร์ต่อเอง
    - ฉันจะ push โค้ดเท่าที่ทำเสร็จขึ้นไปก่อน แล้วขอแรงเพื่อนสักคนมาช่วยรุมดูจุดที่ติดขัดด้วยกันสัก 15 นาที"
